# Alembic migrations

Schema history for NOCTRA. All commands run from the repository root.

## How the environment is wired

- `alembic.ini` holds **no credentials**. `env.py` derives the URL from
  `app.core.config.settings` (`.env` is the single source of truth).
- `env.py` imports `app.core.models_registry`, which imports every model.
  Add new models there — nowhere else — and autogenerate will see them.
- `ALEMBIC_DATABASE_URL` overrides the URL for one command without touching
  `.env`, e.g. a staging check:
  `ALEMBIC_DATABASE_URL=postgresql+asyncpg://… python -m alembic current`
- `ALEMBIC_SCHEMA` runs the whole chain inside an isolated schema. This is
  how `make migrate-check` proves that a fresh install still works without
  touching real tables.

## Everyday commands

```bash
python -m alembic upgrade head          # apply pending migrations
python -m alembic current               # show the applied revision
python -m alembic history --verbose     # full chain
python -m alembic revision --autogenerate -m "add due date to invoices"
python -m alembic downgrade -1          # roll back one revision
python -m alembic check                 # fail if models drift from the DB
```

Autogenerated revisions are a starting point, not the final word. Always
review the operations. Empty revisions are discarded automatically.

## Rules for new migrations

1. **One logical change per revision.** Name it after the intent, not the
   table (`add_invoice_kind`, not `update_invoices`).
2. **Use `CONCURRENTLY` for indexes on large live tables.** Wrap it in
   `with op.get_context().autocommit_block():` and make it re-runnable with
   `IF NOT EXISTS` / `IF EXISTS` — statements outside the transaction stay
   committed even if a later step fails.
3. **Make data backfills idempotent.** Guard with `WHERE … IS NULL`,
   `ADD COLUMN IF NOT EXISTS`, and existence checks before adding
   constraints. The project has databases provisioned both by migrations
   and by `Base.metadata.create_all()`; a revision must work on both.
4. **Validate before constraining.** If a unique constraint could fail on
   existing rows, check first and raise a readable error listing the
   offenders (see `2026_10_21_0002_customers_unique_email_phone.py` and
   `20261030_1300_d4e5f6a7b8c9_schema_reconciliation.py`).
5. **Downgrade must work.** Test `downgrade -1` followed by `upgrade head`
   on a scratch schema before merging.

## Verifying a migration set

```bash
make migrate-check   # upgrade a throwaway schema, then `alembic check`
```

The target runs the entire chain from an empty schema, checks for drift
against the ORM, then drops the scratch objects. A failing check means the
models and migrations disagree; add a revision instead of editing history
that has already been deployed.

## Offline SQL for review

```bash
python -m alembic upgrade head --sql > upgrade.sql
```

Useful when a DBA needs to review DDL before it runs in production. Revisions
using `CONCURRENTLY` emit themselves correctly in offline mode.

## Production checklist

- Back up the database first.
- Apply migrations **before** rolling out new application containers
  (the Docker entrypoint does this via `RUN_MIGRATIONS=1`).
- Run exactly one migrator. Do not let several replicas race; point one
  job/container at `alembic upgrade head`.
- After deploying, run `alembic current` and confirm the expected head.
- `alembic check` is safe to run in CI against a scratch database; do not
  point it at production (it only reads, but a failed check returns 1).
